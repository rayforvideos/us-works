# 구현 품질 기준

함수와 모듈을 나누는 기준, 읽기 쉬운 코드의 형태, 커밋 전 자기 점검 항목을 정한다. 코드를 쓰거나 리뷰할 때 읽는다.

## 관심사 분리

- 한 함수가 생성, 상태 관리, 변환, 오류 처리 중 둘 이상을 하면 분리를 검토한다.
- HTTP, React, DOM 없이 실행할 수 있는 순수 로직은 별도 모듈로 빼고 그 모듈의 단위 테스트로 증명한다. 다른 계층을 거쳐서만 테스트되는 로직을 남기지 않는다.
- 모듈은 자기 상태를 인스턴스 안에 둔다. 모듈 최상위의 가변 변수와 싱글턴은 만들지 않는다(ADR-0005).
- 외부 라이브러리의 실행 순서에 의미가 있으면(인터셉터, 미들웨어, 프로바이더 중첩) 등록을 한 함수 안에 모아 순서를 바꿀 수 없게 하고, 그 순서를 관련 문서에 적는다.

## 크기 상한

- 함수는 60줄, 파일은 150줄을 넘으면 분리 여부를 검토한다. 넘겨도 되지만 이유를 리뷰에서 말할 수 있어야 한다.
- 테스트 파일은 상한을 두지 않는다. 대신 `describe`로 계약 단위를 나눈다.

## 파일 안 순서

- 구현 파일은 import, 타입, UPPER_CASE 상수, 함수 순서로 쓴다. 파일을 열면 코드가 먼저 보이도록 선언은 상단 구역에 모은다.
- 타입 구역의 첫 선언 위에 `@types`, 상수 구역의 첫 선언 위에 `@constants` 표시를 세 줄 JSDoc으로 둔다. 표시는 구역마다 하나이며 다른 곳에는 두지 않는다. 이 두 표시는 주석 금지 규칙의 유일한 예외다.

  ```ts
  /**
   * @types
   */
  type Options = { limit: number };

  /**
   * @constants
   */
  const DEFAULT_LIMIT = 10;
  ```

- camelCase 이름의 `const`(라우트 배열, 인스턴스)는 상수가 아니라 코드로 본다.
- 테스트 파일, `*.d.ts`, `types.ts`, `constants.ts`는 이 규칙을 적용하지 않는다. 나머지는 ESLint `local/section-markers`가 강제한다.

## 조건과 분기

- 있을 수도 없을 수도 있는 의존성(`auth?` 같은 선택 옵션)은 기능을 붙이는 시점에 한 번만 분기한다. 내부 함수마다 `if (!x)`를 반복하지 않는다.
- 실행 조건은 핸들러 안의 조기 반환보다 등록 옵션이나 상위 분기로 올린다. 핸들러 본문은 "실행된다면 무엇을 하는가"만 담는다.
- 같은 조건에서 던지는 오류를 두 곳 이상에서 만들면 이름 있는 헬퍼 하나로 모은다.
- 유니언을 다루는 분기는 `switch`로 모든 값을 다루고 남은 값을 받는 꼬리 분기를 두지 않는다(ADR-0022). `switch-exhaustiveness-check`가 빠진 값을 이름으로 알려준다.
- effect 안에서 최신 props나 상태를 읽어야 하면 ref에 함수를 담아 두지 말고 `useEffectEvent`를 쓴다. effect event는 effect 안에서만 부를 수 있으므로, 같은 일을 이벤트 처리기에서도 해야 하면 그 경로는 일반 함수로 둔다.
- 컨텍스트는 `<Context value={...}>`로 직접 쓴다. `Context.Provider`는 React 19에서 물러날 표현이다.
- 폼 값이 바뀔 때 부모에게 알리는 일은 TanStack Form의 폼 수준 `listeners.onChange`로 한다. 값을 구독해 아무것도 그리지 않는 컴포넌트를 두지 않는다.
- 닫힌 집합은 경계를 넘을 때도 유니언으로 유지한다. 컴포넌트가 값의 집합을 알면 그 타입을 받고, 호출부가 `find`로 다시 좁히지 않는다. 집합의 부분 목록은 `readonly string[]` 대신 `satisfies`로 원소를 검사한다.
- props 일부를 DOM으로 넘기지 않으려고 구조 분해로 덜어낼 때가 있다. 이 경우만 `no-unused-vars`의 `ignoreRestSiblings`로 허용한다. 덜어낸 값을 다시 객체로 묶으면 조합 검증이 풀리므로 원본 props를 그대로 넘긴다.

## 함수 시그니처

- 인자가 셋 이상이면 객체 인자로 바꾼다.
- 호출부에 `null`, `undefined`, `true`, `false`를 위치 인자로 넘기지 않는다. 목적별로 이름이 다른 함수를 두거나 객체 인자에 이름을 붙인다.
- 반환값이 성공 여부와 데이터를 함께 표현해야 하면 판별 가능한 유니언(`{ ok: true, value } | { ok: false, error }`)을 쓴다. `null`로 실패를 표현하지 않는다.

## 비동기

- `async/await`를 기본으로 쓴다. `then` 체인은 한 단계까지만 허용한다.
- 정리 작업은 `finally`에 둔다.
- 동시에 여러 호출자가 같은 비동기 작업을 기다려야 하면 진행 중 Promise 하나를 공유한다. 호출자마다 새 작업을 시작하지 않는다.

## 이름

- 함수 이름은 동사로 시작하고 하나의 동작을 가리킨다. React 컴포넌트는 예외로 PascalCase 명사다. `handle`, `process`, `manage`처럼 무엇을 하는지 드러나지 않는 동사는 쓰지 않는다.
- 불리언은 `is`, `has`, `should`, `can`으로 시작한다.
- 타입, 상수, 파일 이름 규칙은 `docs/file-structure.md`를 따른다.

## 의존성

- pnpm 11부터 `minimumReleaseAge` 기본값이 1440분이다. 배포 24시간이 지나지 않은 버전은 설치 대상에서 제외되므로, `pnpm update`가 npm 최신 버전을 올리지 않는 것은 정상이다.
- `pnpm add pkg@정확한버전`으로 강제하면 pnpm이 `minimumReleaseAgeExclude`에 그 패키지를 자동으로 더하고, 이후 `pnpm` 명령이 lockfile 공급망 검사에서 실패한다. 우회하지 않고 하루 뒤 `pnpm update`로 올린다.
- pnpm 12는 의존성의 postinstall 스크립트를 기본 차단한다. 필요한 패키지만 `pnpm-workspace.yaml`의 `allowBuilds`에 적는다.

## 커밋 전 자기 점검

커밋마다 다음을 스스로 묻고, 하나라도 "아니오"면 커밋 전에 고친다.

1. 새로 만든 함수가 한 문장으로 설명되는가.
2. 순수 로직이 HTTP나 React를 거쳐서만 테스트되고 있지 않은가.
3. 같은 `if` 조건이 두 곳 이상에 반복되지 않는가.
4. 호출부에 위치 인자 `null`이나 불리언 리터럴이 없는가.
5. 등록 순서에 의미가 있는 코드가 한곳에 모여 있고 문서에 적혀 있는가.
6. 60줄이 넘는 함수가 있다면 그 이유를 말할 수 있는가.
