# ADR-0017: Place Single-Consumer Modules in Page Segments

## Status

Accepted

## Context

ADR-0002는 `pages`를 라우트 단위 화면 조합으로, `features`를 사용자 행위 단위 기능으로 정의했다. 그 정의대로 콘텐츠 작성 폼, 발행 옵션, 알림 작성 폼을 각각 `features` 슬라이스로 만들었더니 셋 다 소비자가 페이지 하나뿐이었고, steiger의 `fsd/insignificant-slice`가 매번 이를 지적했다. 이슈 #31에서 임시 예외를 달아 두었다가 예외를 지우기로 하고 세 슬라이스를 각 페이지의 세그먼트로 옮겼다. 지금 `features`에는 소비자가 둘 이상인 `auth`와 `start-content`만 남아 있고, 이 규칙은 `docs/file-structure.md`에만 적혀 있다.

비교한 선택지는 다음과 같다.

- 기능 슬라이스를 유지하고 예외를 영구화: 도메인 단위 이름이 남지만, 규칙을 끄는 설정이 계속 쌓이고 임시 예외를 반드시 지운다는 원칙과 어긋난다.
- 페이지 세그먼트로 이동: 예외가 사라지고 한 화면의 폼·스키마·요청이 한 곳에 모인다. 페이지 슬라이스가 커지고, 두 번째 화면이 쓰게 되면 다시 올리는 비용이 든다.
- 도메인별로 하나의 큰 기능 슬라이스로 합치기(예: `features/content`): 슬라이스 수는 줄지만 한 슬라이스가 여러 행위를 담아 FSD의 행위 단위 구분이 흐려진다.

## Decision

- 소비자가 페이지 하나뿐인 폼, 스키마, 요청 훅은 그 페이지 슬라이스의 `model`, `api`, `ui` 세그먼트에 둔다. ADR-0002의 `pages` 정의를 이 범위까지 넓힌다.
- 두 번째 화면이 같은 모듈을 쓰게 되면 `features`나 `entities`로 올리고, 그때 슬라이스 이름을 정한다.
- 페이지 슬라이스의 `index.ts`는 라우트 진입 컴포넌트만 공개한다. 페이지 안의 모듈은 상대 경로로만 참조한다.
- `fsd/insignificant-slice`를 끄는 예외는 두지 않는다. 규칙에 걸리면 예외 대신 배치를 바꾼다.

## Consequences

**좋은 점**

- 정적 검사를 끄지 않고 규칙을 지키며, 한 화면을 고칠 때 볼 파일이 그 페이지 아래에 모인다.

**나쁜 점과 감수하는 위험**

- 페이지 슬라이스의 파일 수가 늘어 `pages/content-write`처럼 세그먼트 셋을 모두 가진 페이지가 생긴다. 모듈 이름과 폴더 구조는 옮기기 전과 같게 두어 이동 비용을 낮춘다.
- 다시 볼 조건: 한 페이지의 모듈이 한눈에 들어오지 않을 만큼 늘거나, 두 번째 소비자가 생겨 승격이 잦아지면 도메인 단위 기능 슬라이스를 다시 검토한다.
