# ADR-0021: Define Query Keys and Options in Entity Factories

## Status

Accepted

## Context

TanStack Query 훅은 지금 엔드포인트마다 모듈 하나다. 조회 훅 다섯 개가 각자 `useQuery`를 감싸고 쿼리 키를 배열 리터럴로 적는다. 무효화하는 쪽은 뮤테이션이라 키를 다시 적는다. 키 리터럴은 일곱 파일에 열한 번 있고 단일 출처가 없다. 정의와 무효화가 어긋나도 컴파일러가 잡지 못해, 알람 수정 뮤테이션이 콘텐츠 캐시를 무효화하지 않는 결함이 이미 생겼다. 화면은 30초 동안 옛 값을 보인다.

비교한 선택지는 다음과 같다.

- 지금 구조 유지: 훅 이름만 보면 무엇을 부르는지 알 수 있다. 다만 키가 흩어진 문제가 그대로이고, 엔드포인트가 늘 때마다 모듈 셋(구현, `index.ts`, 디렉토리)이 는다.
- 키 팩토리만 추가: 키의 단일 출처가 생기고 변경 범위가 작다. 훅 모듈은 그대로 남아 엔드포인트마다 같은 세 줄을 다시 쓴다.
- `queryOptions` 팩토리(TanStack Query 5의 방식): 키와 조회 함수, 옵션을 엔티티의 한 파일에 모으고 화면이 `useQuery(contentQueries.detail(client, id))`로 쓴다. 훅 모듈이 사라지고 키에 이름이 붙는다. 화면이 `useHttpClient()`를 직접 불러 클라이언트를 넘겨야 한다.
- 요청 함수 이름이나 인자에서 키를 자동 생성: 키를 적을 일이 없다. 대신 키가 코드에서 사라져 부분 무효화를 표현할 수 없고, 번들러가 이름을 바꾸면 조용히 어긋난다.

## Decision

- 조회의 키와 옵션은 엔티티의 `api` 세그먼트에 있는 팩토리 한 곳에서 만든다. 팩토리는 `queryOptions()`를 돌려주고 화면은 그것을 `useQuery`에 넘긴다. 엔드포인트마다 훅 모듈을 만들지 않는다.
- 팩토리는 무효화 단위를 이름으로 공개한다. 엔티티 전체, 목록, 상세처럼 단계를 나눠 두고 뮤테이션은 배열 리터럴 대신 그 이름을 쓴다.
- 키는 `[엔티티, 동작, 파라미터]` 모양을 유지한다. 함수 이름이나 인자에서 키를 자동으로 만들지 않는다.
- 뮤테이션은 훅으로 남긴다. 무엇을 무효화하고 어떤 순서로 부를지가 화면마다 다른 정책이라 공통 껍데기에 넣지 않는다.
- 요청 함수는 지금처럼 엔티티의 `api`에 두고 클라이언트를 첫 인자로 받는다. 이 결정은 훅의 자리만 바꾼다.

## Consequences

**좋은 점**

- 키의 출처가 하나라서 무효화 범위가 컴파일러의 확인을 받는다. 키 모양이 바뀔 때 고칠 곳이 다섯 파일에서 한 파일이 된다.
- 엔드포인트가 늘어도 파일이 늘지 않는다. 조회 훅 모듈 다섯 개가 팩토리 둘로 줄어든다.

**나쁜 점과 감수하는 위험**

- 화면이 `useHttpClient()`를 직접 불러 팩토리에 넘겨야 해서 호출부가 한 줄 늘어난다.
- 훅 이름으로 찾던 조회를 이제 팩토리 안에서 찾는다. 엔티티마다 파일 하나라 찾는 범위는 좁다.
- 다시 볼 조건: 한 엔티티의 조회가 팩토리 파일 하나에 담기 어려울 만큼 늘거나, 조회마다 서로 다른 캐시 정책이 필요해지면 다시 훅으로 나눌지 검토한다.
