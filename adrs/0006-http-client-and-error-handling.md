# ADR-0006: Use Axios with Expiry-Aware Token Refresh and Normalized Errors

## Status

Accepted

## Context

모든 API 요청은 `{ success, data, error }` 로 응답하고, 인증이 필요한 요청은 `Authorization: Bearer <access_token>` 헤더를 요구한다. Access Token은 발급 15분 뒤 만료되며, 만료 후에는 Refresh Token으로 재발급받아 요청을 다시 보내야 한다. 로그인 응답에는 만료 시각 `access_expires_at`이 들어 있고, 과제 사양은 이 값으로 만료를 확인하고 만료 후 재발급과 재시도를 구현하라고 명시한다.

이 처리를 담는 HTTP 클라이언트는 `shared/api`에 하나만 두고, ADR-0005에 따라 토큰 접근자와 갱신 핸들러를 주입받는다. 결정할 것은 네 가지다. 어떤 HTTP 라이브러리를 쓸지, 토큰 갱신을 언제 할지, 갱신 중에 들어오는 여러 요청을 어떻게 다룰지, 실패를 화면에 어떤 형태로 전달할지다.

세 번째가 가장 실수하기 쉽다. 목록 화면은 콘텐츠 목록, 알림 목록, 사용자 정보처럼 여러 요청을 동시에 보내는데, 토큰이 만료된 순간 이 요청들이 모두 401을 받는다. 요청마다 갱신을 호출하면 Refresh Token으로 재발급이 여러 번 일어나고, 서버가 이전 Refresh Token을 무효화하는 경우 나중 갱신이 실패해 사용자가 로그아웃된다. 갱신 실패 시 로그아웃 처리가 여러 번 실행되는 문제도 생긴다.

네 번째도 정하지 않으면 화면마다 axios 오류 객체를 직접 뒤져 문구를 만들게 된다. 서버 응답의 `error` 필드는 문자열 하나뿐이고 오류 코드가 없어서, 분류 기준을 클라이언트가 정해야 한다.

## Decision

- HTTP 라이브러리로 axios를 사용한다. 요청과 응답 인터셉터로 헤더 부착, 만료 확인, 응답 데이터 추출, 401 처리, 오류 정규화를 한 곳에 두고, 취소는 axios가 지원하는 `AbortSignal`을 TanStack Query에서 그대로 넘긴다.
- 클라이언트는 `shared/api/http-client/`의 `createHttpClient()` 팩토리로 axios 인스턴스를 만들어 반환한다. 팩토리는 기본 URL, 토큰 접근자, 갱신 핸들러, 인증 실패 핸들러를 받고, 테스트를 위해 axios `adapter`와 현재 시각 함수를 주입할 수 있게 한다.
- 토큰 접근자는 토큰과 만료 시각을 함께 돌려준다. 인증 요청을 보내기 직전에 만료 시각을 확인해 이미 지났거나 60초 안에 만료되면 먼저 갱신하고 새 토큰으로 보낸다. 타이머 기반 선제 갱신은 하지 않는다.
- 만료 확인은 요청당 한 번만 한다. 갱신 뒤에도 만료로 판정되면(클라이언트 시계 오차) 그대로 보내고 결과는 401 처리에 맡긴다. 갱신 루프를 막기 위해서다.
- 401 응답은 만료 확인을 통과했더라도 최종 판정으로 취급한다. 401을 받으면 갱신을 시도하고, 성공하면 원 요청을 새 토큰으로 한 번만 재시도한다.
- 갱신은 항상 단일 실행(single-flight)이어야 한다. 만료 확인이든 401이든 갱신이 진행 중이면 새 갱신을 시작하지 않고 진행 중인 갱신 Promise를 함께 기다린다. 갱신이 끝나면 대기하던 모든 요청이 각자 새 토큰으로 한 번씩 보낸다.
- 갱신이 실패하면(핸들러가 false를 반환하거나 예외를 던지면) 대기 중이던 모든 요청은 `unauthorized` 오류로 실패하고, 인증 실패 핸들러는 정확히 한 번만 호출된다. 갱신 후 재시도한 요청이 다시 401을 받아도 같은 처리를 한다.
- 로그인, 회원가입, 토큰 갱신 요청은 `skipAuth` 표시를 달아 헤더 부착, 만료 확인, 갱신 대기, 401 재시도에서 모두 제외한다. 갱신 요청 자체가 갱신 흐름에 들어가는 순환을 막기 위해서다.
- 클라이언트를 통과한 모든 실패는 `ApiError` 하나로 정규화한다. `kind`(분류), `status`(HTTP 상태 코드, 응답이 없으면 null), `message`(응답의 `error` 필드, 없으면 null), `cause`(원본 오류)를 가진다. 네트워크 실패와 취소도 `ApiError`로 감싼다.
- `kind`는 HTTP 상태 코드로 정한다. 응답 없음은 `network`, 취소는 `canceled`, 401은 `unauthorized`, 403은 `forbidden`, 404는 `not_found`, 409는 `conflict`, 400은 `validation`, 5xx는 `server`, 그 외는 `unknown`이다.
- 사용자에게 보이는 문구는 `shared/lib`의 한 함수가 `kind`로 결정한다. `validation`과 `conflict`만 서버 문구를 그대로 쓰고 나머지는 고정 문구다. 화면은 `ApiError.message`를 직접 출력하지 않는다. ADR-0012가 이 항목을 대체한다.
- TanStack Query의 재시도는 `kind`가 `network` 또는 `server`일 때만 한다. `validation`, `conflict`, `not_found`, `forbidden`, `unauthorized`, `canceled`는 재시도하지 않는다. 이 정책은 `createQueryClient()`의 기본 `retry` 함수에 둔다.
- 단일 실행, 대기, 실패 전파, 만료 확인, 오류 분류는 테스트로 증명한다. 동시에 N개 요청이 401을 받을 때 갱신 호출은 1회, 재시도는 각 1회, 갱신 실패 시 인증 실패 핸들러 호출은 1회여야 한다.

## Consequences

**좋은 점**

- 인터셉터 한 곳에서 인증, 응답 데이터 추출, 오류 처리가 끝나 엔드포인트 함수는 요청과 응답 타입만 다룬다.
- 만료가 임박한 토큰은 요청 전에 갱신되어 만료 직후 401 왕복이 사라진다. 사양이 요구하는 `access_expires_at` 활용을 그대로 충족한다.
- 토큰 만료 순간 여러 요청이 몰려도 갱신은 한 번만 일어나 Refresh Token 재사용 문제와 중복 로그아웃이 생기지 않는다.
- 타이머를 쓰지 않아 탭 비활성이나 시계 드리프트를 관리할 필요가 없고, 401 폴백이 시계 오차와 서버 측 무효화를 흡수한다.
- 화면은 `kind` 하나로 분기하고 문구는 한 곳에서 관리되어, 오프라인과 서버 오류와 입력 오류가 다른 안내를 받는다.
- 재시도가 실패 종류에 따라 갈려 400이나 409에 무의미한 재요청을 보내지 않는다.
- 동시성과 오류 규칙이 테스트로 고정되어 리팩터링 중 회귀를 잡는다.

**나쁜 점과 감수하는 위험**

- axios 의존성이 추가된다. JD에는 없는 라이브러리지만 표준적이라 평가자에게 설명이 필요하지 않다.
- 절대 시각 비교라 클라이언트 시계가 서버와 다르면 판정이 어긋난다. 60초 여유와 요청당 1회 확인, 401 폴백으로 영향을 갱신 한 번 낭비 수준으로 제한한다.
- 갱신 대기 큐와 단일 실행 로직은 인터셉터 안에서 가장 복잡한 부분이다. 상태(진행 중 Promise)를 클라이언트 인스턴스 안에 가두고 모듈 전역에 두지 않는다.
- 재시도는 한 번뿐이어서 갱신 직후 서버가 일시적으로 401을 돌려주면 로그아웃된다. 서버 동작상 갱신 성공 후 토큰이 즉시 유효하므로 허용한다.
- 서버가 오류 코드를 주지 않아 `kind` 분류가 HTTP 상태 코드에 묶인다. 같은 400 안에서 세부 원인을 나눠야 하면 서버 문구에 의존해야 한다.
- 토큰 접근자 계약이 토큰만 돌려주는 형태보다 넓어져, 세션 상태를 관리하는 엔티티가 만료 시각도 저장해야 한다.
