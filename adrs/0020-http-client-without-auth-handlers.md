# ADR-0020: Treat an HTTP Client Without Auth Handlers as a Valid Configuration

## Status

Accepted

## Context

ADR-0005는 HTTP 클라이언트가 토큰 접근자와 갱신 핸들러를 주입받기로 하면서, 미설정 상태에서 호출되면 명시적으로 오류를 던지게 한다고 적었다. 구현은 그렇게 하지 않는다. `createHttpClient()`는 `auth` 옵션이 없으면 인증 인터셉터를 등록하지 않고 요청을 그대로 보낸다.

`initializeSystem()`이 클라이언트를 둘 만들기 때문이다. 갱신 핸들러는 `POST /api/v1/auth/refresh`를 보낼 클라이언트를 필요로 하고, 그 요청을 인증 클라이언트로 보내면 갱신 흐름이 자기 자신을 다시 부른다(ADR-0006). 그래서 `auth` 없는 클라이언트를 먼저 만들어 갱신 요청에만 쓰고, 그 클라이언트를 갱신 핸들러에 넘겨 인증 클라이언트를 만든다. 미설정 호출에서 오류를 던지면 이 순서를 만들 수 없다.

비교한 선택지는 다음과 같다.

- ADR-0005의 원안대로 오류 던지기: 주입을 잊은 실수가 첫 요청에서 드러나지만, 갱신 전용 클라이언트를 만들 수 없어 생성 순환을 다른 장치로 풀어야 한다.
- 늦은 설정 함수로 클라이언트 하나를 나중에 설정하기: 인스턴스는 하나로 줄지만 설정 전후로 동작이 다른 시간 창이 생기고, 초기화 순서가 코드에서 드러나지 않는다.
- `auth`가 없으면 인증 처리를 건너뛰기: 순환이 사라지고 팩토리가 옵션 하나로 두 구성을 다 만든다. 대신 주입을 잊으면 토큰 없는 요청이 나가고 401로만 드러난다.

## Decision

- `auth` 옵션 없이 만든 HTTP 클라이언트를 정상 구성으로 인정한다. 팩토리는 인증 인터셉터를 등록하지 않고 오류도 던지지 않는다. ADR-0005의 해당 항목을 대체한다.
- `auth` 없는 클라이언트는 헤더를 붙이지 않고 만료 확인과 갱신 대기를 하지 않으며, 401을 `unauthorized` `ApiError`로 던진다.
- 토큰 갱신 요청은 `auth` 없는 전용 클라이언트로 보낸다. 갱신 핸들러가 클라이언트를 받고 그 클라이언트가 다시 그 핸들러를 받는 순환을 만들지 않기 위해서다.
- 화면과 훅은 클라이언트를 직접 만들지 않고 `HttpClientProvider`가 넘긴 인증 클라이언트를 `useHttpClient()`로 받는다. 인증 요청이 갱신용 클라이언트로 나가지 않게 하는 장치는 이 주입 경로 하나다.

## Consequences

**좋은 점**

- 초기화가 생성 순서만으로 끝나고, 갱신 요청이 갱신 흐름에 다시 들어가지 않는다.
- 팩토리가 인증 있는 구성과 없는 구성을 같은 코드로 만들어 테스트는 필요한 쪽만 골라 만든다.

**나쁜 점과 감수하는 위험**

- `auth` 주입을 잊으면 토큰 없는 요청이 나가고 401로만 드러난다. 클라이언트를 만드는 자리를 `initializeSystem()` 하나로 묶어 실수 범위를 좁힌다.
- 다시 볼 조건: 갱신 전용 말고도 `auth` 없는 클라이언트가 늘거나 인증 요청이 잘못된 클라이언트로 나가는 일이 실제로 생기면, 구성을 강제하는 방식을 다시 본다.
